## Collection And Four Sessions

`backend-reference` runs the existing metadata/operator controls, then the full
original discovery from the isolated `source/backend` directory, with
`--collect-only` added. It includes audit modules outside `backend/tests`.
The collection plugin observes actual `item.path`, full node IDs, rootdir,
configuration, import mode and required plugins. It cannot select or reorder
items. Collection errors, duplicates, discovery drift and deselection reject
the reference. A collection-only plan makes no phase/test-success claim.

Collected module paths must be canonical committed regular Python files.
Sorted paths are assigned `index % 4`; every assigned module runs serially,
with its complete reference-ordered identities. Workers retain the real
reference rootdir/config/import mode and the existing evidence, snapshot and
storage plugins. No `xdist`, keyword expression, arbitrary test argv, rerun,
threshold or tests-directory-only replacement is used.

The required job named `backend` runs even when prerequisites fail. It requires
reference and matrix job success, four different shard identities, identical
bindings/runtime, genuine runner and pytest exits zero, sanitizer exit zero,
and the unchanged auditor's complete/success-consistent verdict. Each worker's
ordered identities must equal its assignment. Their disjoint Counter union
must equal the full reference, whose original global order is retained in the
plan/result. This describes **four real serial sessions**, not one invented
global execution order or a synthetic monolithic session.

Every ordinary phase and subtest occurrence is retained. Phase requirements
follow the old auditor, including skipped setup behavior. Existing skips/xfails
are not relabeled as passes, and failed ordinary or subtest reports veto the
join. A sanitizer returning zero for valid failure metadata is not success.

## Runtime And Deadline

Reference and all four workers use `ubuntu-24.04`, CPython `3.12.3`, Linux
`x86_64`, glibc `2.39`. Each hosted job creates a fresh venv and installs the
unchanged complete `requirements-py312-linux.lock` using binary wheels and
`--require-hashes`. All 28 application package identities must exactly match
the lock and reference. Missing, extra, duplicate or changed packages fail.
Installer `pip` alone is excluded; this does not certify its version, provider
or byte identity. No author-host install is part of this change.

Reference and worker VMs each run their own existing fixed-SDK capacity admission
before creating the application venv or installing packages. The helper accepts
only the exact legacy `backend`, `backend-reference` and `backend-workers` job
names, retaining all other hosted-context, path, symlink and deletion checks.
No job identity is forged, and one VM's cleanup is not transferred to another.

The first reference/worker step records one monotonic work deadline, 330 minutes
from that step, including checkout, setup, install, prechecks, source/private
preparation, collection and execution. Bootstrap actions have finite step
limits; later commands use the original remaining budget, not a fresh one.
Jobs remain bounded at 360 minutes. Game/AI limits are unchanged.

The genuine pytest process owns a new session. A purpose-bound watcher records
PID, parent, start, process group and session. At the deadline it revalidates
that exact identity before INT and again before KILL, 15 seconds later. A
failed watcher is observed alongside pytest with `wait -n`; it cannot leave a
silently unbounded normal wait. The parent retains the genuine wait result and
writes it promptly. Deadline/identity/diagnostic failure is separate from that
pytest exit, and can never turn failure into success.

Leader exit is **not** registered-group closure. The actual CLI separately
queries its recorded process group with signal zero: only ESRCH means absent;
presence, EPERM, other errors or missing original registration veto success.
After leader exit only a bounded natural drain is observed; no further signal
is sent without the original leader-incarnation proof. Fresh group-empty checks
also run after the genuine wait and during final cleanup. A reused group is
not permission to signal it. This observes the exact registered group only,
NOT every session member, escaped descendant or hostile process. No global PID
scan/universal descendant-reap guarantee is claimed. The historical fake-callback
API performs no OS query; its leader-only result is not a group certificate.

Only pinned owned diagnostic children are stopped/reaped. Pressure, sink,
sampler, progress, watcher and logger share at most 120 seconds of shutdown
observation (time spent in the separately bounded auditor is not a new shutdown
budget). Only progress's existing graceful TERM is an intended normal stop;
other forced cleanup, nonzero waits or unknown closure fail. Auditor/context
admission shares 120 seconds; sanitizer and envelope steps each have a finite
120-second command bound; uploads have five-minute step bounds. Kernel-blocked
or unidentifiable processes are UNKNOWN failures, never a guaranteed reap.

Legacy runner mode remains for the original runner protocol tests. Its argv,
private source preparation, storage reserve, media archive, snapshot policy
and actual pytest-status file remain; sampler/cleanup waits are now finite.
The separate legacy adaptation changes only two workflow-publication methods
and one progress-layout method for the exact four upload definitions and two
secret-bearing definitions (one reference plus four matrix instances). All real
runner/privacy/progress control bodies remain unchanged. The metadata name/id,
single `metadata_file` output and fixed READY/FAILED behavior are restored so
the actual metadata and inherited partial-workflow tests stay byte-identical.

## Private Inputs And Artifact Admission

Each reference/worker independently uses the existing 13-chunk protected-input
preparer, only in its secret-bearing hosted step after stdout/stderr have been
routed to the existing private bounded streams. Hash, size, exclusive creation
and environment-unset logic are unchanged. Missing input is failure, not skip.
No decoded input is transported, read locally, or uploaded. No secret is needed
by the final join job. Frontend/browser jobs are byte-preserved.

Uploads name only `plan.json`, `worker.json`, the final validated result, or the
unchanged sanitizer's exact schema-v1 `backend-metadata.json` diagnostic;
never logs, scratch, evidence directories or wildcard paths. Public module
paths come from committed source; complete node identities are UTF-8 SHA256
hashes, never names/parameters. The envelope forwards only an explicitly
validated core projection of the existing sanitizer: complete audit fields,
discovery/session observations, all phase/subtest rows, and real exit statuses.
Optional local timing/diagnostic reports are not arbitrary transport fields.

Worker diagnostics have a distinct always/available upload, including valid
failure or partial/incomplete reports. The unchanged sanitizer remains the
raw-to-public boundary; an additional 64-MiB regular-file/top-schema bound checks
its exact JSON without rewriting it or certifying success. Existing safe timing
and partial/failure fields remain in that diagnostic document. Its artifact name
binds worker/run/attempt/commit/plan/shard; final join never downloads or consumes
diagnostic artifacts. Metadata exit zero for successful-envelope admission is
derived from the actual successful metadata step, not an added output. A
reference collection failure is not exported as execution-success metadata.

Fixed limits reject rather than truncate: plan 16 MiB, 4,096 modules, 100,000
nodes; worker 64 MiB, 300,000 phases, 100,000 subtests. Duplicate JSON keys,
nonfinite numbers, boolean/integer aliases, unknown fields, extra artifact
members and linked inputs fail. Run ID, attempt, full commit, source archive,
lock and plan hash bind all records. Reference download uses its exact same-run
artifact ID; four workers use exact unique names into four separate directories.
No wildcard merge or cross-run fallback is accepted.

Upload uses existing pin `ea165f8d65b6e75b540449e92b4886f43607fa02`;
download uses official pin `d3f86a106a0bac45b974a628896c90dbdf5c8093`.
Permissions remain `contents: read`; no fork/secret bypass or new credential scope.
