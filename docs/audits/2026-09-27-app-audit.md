# MTG app audit — TypeScript, application flows, and release readiness

Audit date: 2026-09-27 UTC. Repository: `/home/nick/mtg-deck-testing-lab`.
Revision: `6b95fab0875f4cc35cb9648f8a598be5b13b2c80`, branch `main`.

## Bottom line

**The frontend compiles, and the backend has substantial regression coverage, but this is not yet a finished, reliable human-playtesting application.** The most consequential problems are integration gaps that TypeScript cannot detect: live-match hydration drops card faces, the UI cannot play the second human seat or several legal actions, displayed combat stats disagree with engine stats, and ordinary turn actions bypass supported replacement/trigger logic.

A small deterministic AI replay passes. That is encouraging, not evidence of arbitrary-card correctness, balanced AI, or finished UI flows. “Finished” should first mean a reliable local desktop app for an explicitly supported card corpus; unrestricted Magic rules support and expert-level AI are separate, much larger goals.

No fixes, deployment, or changes to original app source were made.

## Prioritized findings

### P1 — Live match hydration loses double-faced/modal card data

**Reproduced.** `backend/main.py:1153-1206` hydrates cached cards for `/matches/start` but never transfers `card_faces_json`. By contrast, the diagnostics helper does (`backend/card_data/hydration.py:33-40`). `MatchFactory` only receives faces from the hydrated item (`backend/game_state/state.py:210-216`). Normal UI deck payloads contain names and quantities (`frontend/src/App.tsx:53-59`; `frontend/src/types/index.ts:1-10`).

A cached two-face fixture produced **0 faces in the API path, 2 in the diagnostic path**. Thus passing face-aware engine/diagnostic tests do not establish that a user-created live match can use the same functionality. The response serializer also omits face metadata from card views (`backend/game_state/serializers.py:247-274`).

**Finish requirement:** use one canonical hydration contract for API, sideboarding, analytics, and replay, and expose necessary face data in serialized views. Acceptance: import/cache a real modal/transform card, start via HTTP using only deck names/quantities, assert both faces survive state and restart, then choose/transform legally through the UI and verify resulting types/stats.

### P1 — Advertised human flows cannot issue all supported actions

**Reproduced render gap; code-confirmed action wiring.** `Battlefield.tsx:121-129` sends casts as player 1; hand controls iterate only `p1.hand` (`:406`); mana, loyalty, cycling and equipment controls likewise hard-code player 1 (`:285-291`, `:310-317`, `:375-380`, `:436`). Human-vs-human is offered and sent to the API (`App.tsx:14,60-63`). A rendered human-vs-human state with seat 2 priority displays seat 1's card, not seat 2's card or play button.

Backend legal moves include generic `activate_ability`, `crew`, and exile play (`backend/rules_engine/move_generator.py:218-236,324,356-379`), but the frontend action filters handle casting/cycling/land/loyalty/equip only (`Battlefield.tsx:93-98`); a source-wide search found no generic ability or crew controls. Rendering those legal moves yields no action control. Hand-only rendering also leaves exile/top-library play without a general zone/action UI.

**Finish requirement:** drive a typed action/choice renderer from the actual acting seat and legal moves, not player-1 hand iteration. Acceptance: play a complete human-vs-human game; activate a non-loyalty permanent ability, crew a Vehicle, and play a permitted exile card using only UI controls. Every actionable legal move must either have a control or an explicit unsupported warning; no silent omissions.

### P1 — Turn draw and cleanup bypass supported rules events

**Reproduced.** Normal turn draw calls raw `draw_card` (`backend/rules_engine/engine.py:87-93`; `game_state/state.py:231-244`) instead of the replacement-aware effect path (`effects/handlers.py:209-233`). With a replacement phrase already recognized by the engine (`rules_engine/replacement.py:98-103`), a turn draw adds one card and zero life, while the effect draw correctly adds zero cards and one life.

Cleanup directly pops the first hand card into the graveyard (`rules_engine/engine.py:233-245`). It neither lets a human choose discards nor emits the normal discard event. An 8-card hand plus a supported discard trigger yields **0 cleanup triggers vs 1 from the ordinary discard effect**, with both ending at seven cards. Existing cleanup tests assert hand size only (`backend/tests/test_cleanup_hand_size.py:7-28`).

**Finish requirement:** route all draw/discard sources through shared event-aware operations, with human choice and resumable replacement handling. Acceptance: the same replacement/trigger fixture must behave identically for draw-step, spell, cycling, and cleanup sources where rules permit; test cleanup choice, ownership, trigger ordering, and snapshot resume.

### P1 — The battlefield reports base rather than effective combat stats

**Reproduced.** API serialization returns `card.power/toughness` (`backend/game_state/serializers.py:253-254`), and the UI renders those values (`Battlefield.tsx:186,249`). The rules engine computes counters, continuous effects, and temporary bonuses separately (`backend/rules_engine/continuous.py:116-133`). A 2/2 with a +1/+1 counter fights as **3/3** but is exposed to the UI as **2/2**.

**Finish requirement:** serialize effective stats, relevant counters, damage and effective keywords distinctly from printed/base values. Acceptance: counter, anthem, temporary pump, characteristic-defined stats, and cleanup expiration must match combat resolution and hover display before/after reload.

### P1 release gate — A clean source checkout fails tests because a required fallback asset is ignored

**Reproduced.** `backend/tests/test_api_smoke.py:22-27` requires `/card-images/generic-token-creature.svg` to return 200; `backend/tests/test_token_images.py:21` requires its filename. The resolver uses that SVG only when already present (`backend/card_data/token_images.py:29-34`). The entire image cache is ignored (`.gitignore:14`), no generic SVG is tracked, and startup merely creates the cache directory (`backend/main.py:63-64`). The existing developer checkout does contain the ignored SVG.

The tracked-only checkout returned **404** and a different placeholder filename. Copying that one asset into scratch made both failing tests pass. This is a packaging/test-fixture defect, not proof that all runtime fallback rendering is broken: a generated per-card placeholder does exist.

**Finish requirement:** ship a canonical fallback outside the disposable cache, generate it deterministically, or make tests verify the intended generated fallback contract. Acceptance: fresh checkout + declared dependencies + empty database/cache passes the entire suite and serves offline art without borrowing files from a developer machine.

### P2 — API input contracts allow invalid games and produce internal server errors

**Reproduced.** `StartMatchRequest` accepts `list[dict]`, and actions are arbitrary dictionaries (`backend/main.py:96-120`). `/matches/start`, legal-move queries, and action endpoints forward unchecked nested data (`:492-496,564-570,602-610`).

Saved HTTP probe results:
- Empty or negative-quantity deck: **200**, immediately lost game (`winner: 2`).
- Deck item missing quantity: **500**.
- `play_land` without card ID: **500**.
- Legal moves with `player_id=99`: **500**.

**Finish requirement:** typed bounded deck entries and discriminated action schemas; distinguish sandbox deck-size rules from malformed data; validate players/action prerequisites and return structured 4xx errors. Acceptance: fuzz missing fields, invalid IDs, negative/oversized quantities and unsupported actions; verify 4xx responses and unchanged authoritative state. Do not merely swallow exceptions after partial mutation.

### P2 — Match recovery, error feedback, and mutation coordination are unfinished

**Code-confirmed.** App match state exists only in component memory (`frontend/src/App.tsx:17`); startup only checks health/loads decks, with no frontend persisted match ID/resume path. A refresh loses the visible match even though backend snapshots exist. Most action handlers await API writes without catches or a pending-action guard (`App.tsx:49-178`). The fetch wrapper has no timeout/cancellation or runtime response validation (`api/client.ts:168-177`); auto-loop failures only log to console (`App.tsx:195-208`).

This establishes missing controls, not a reproduced race. Concurrent/stale response overwrites are a credible follow-up risk because manual actions and auto-progression can overlap; no load/concurrency exploit was attempted.

**Finish requirement:** active-match discovery/resume, request cancellation/stale-result rejection, mutation serialization, visible actionable errors and retry semantics. Acceptance: refresh midgame, restart backend, disconnect during action, double-click and overlap autoplay/manual actions; never lose access to a saved match or apply the same action twice.

### P2 — Production routing default contradicts the documented reverse-proxy path

**Code-confirmed, deployment outcome conditional.** Production fallback is hard-coded `http://${hostname}:9999` (`frontend/src/api/client.ts:3-8`), while README says a reverse-proxy deployment can keep default `/api` routing (`README.md:152`). On an HTTPS page this fallback is mixed-content HTTP; behind a same-origin proxy it bypasses the proxy unless `VITE_API_BASE_URL` was explicitly set at build time.

**Finish requirement:** default to same-origin `/api` or clearly require and validate the deployment variable; keep card-media routing consistent. Acceptance: serve the real built artifact under HTTPS with `/api` and `/card-images` proxy routes, test health/import/start/action, and separately test a configured cross-origin backend. A development Vite proxy check is not sufficient.

### P2 — BO3 live-match behavior differs from deterministic diagnostic behavior

**Code-confirmed, starting-player transition reproduced.** `_start_next_game_state` calls `MatchFactory.from_decks` without a seed (`backend/main.py:1221-1226`) and assigns the starting player using the pre-increment game number (`:1238-1243`). Probe: game 1 starts with P1 and game 2 also starts with P1. There is no previous-loser play/draw choice here. Diagnostic BO3 instead explicitly passes `seed + game_index` (`backend/scripts/regression_matrix_replay.py:112`).

**Finish requirement:** define the intended tournament/sandbox start-player policy, expose loser choice when appropriate, preserve per-game seed provenance, and implement deliberate AI sideboarding or label it absent. Acceptance: repeat the same seeded interactive BO3 action sequence and restart between games; identical starts/decks/outcomes where actions match, validated sideboard transitions, correct play/draw choice. Diagnostic determinism alone does not cover this API route.

### P2 — TypeScript passes, but it is not a contract or UI regression gate

**Code-confirmed and command-verified.** `strict: true` is already enabled (`frontend/tsconfig.json:13`); do not waste a task “enabling strict mode.” There is no lint/test script (`frontend/package.json:6-10`), no tracked frontend test suite/CI workflow, response JSON is cast rather than validated (`api/client.ts:177`), and `result?: any` weakens simulator typing (`:119`). Example schema drift: frontend `MatchState.blocks` is `Record<string,string>` (`types/index.ts:64`), while backend block assignments are lists (`game_state/serializers.py:25`, public `:294`).

**Finish requirement:** generated or shared OpenAPI types, runtime validation at API boundaries, discriminated legal-action/choice types, ESLint React-hooks checks, component tests and browser smoke tests. Acceptance: wrong block payload or missing card-view field fails a contract test; tests cover every P1 above and run with build/lint in CI. Additional strictness flags are useful after the meaningful boundary types are fixed.

### P2 before network exposure — Security and resource-lifecycle hardening

**Code-confirmed surface; exposure/exploitability unverified.** CORS allows every origin/method/header (`backend/main.py:55-62`), route dependencies provide repositories but no authentication/authorization, and match mutation is globally addressable by ID. Each batch-start call creates a daemon thread (`:735-791`), without a bounded queue in that path. Active matches live in a process-global dictionary (`:84`), with mutation endpoints not using a per-match lock. Thus multiworker consistency and simultaneous writes need explicit design/testing; they are not proven broken by a stress test here.

The current registry audit flags 7 frontend dependency packages, including Vite, browserslist, nanoid and postcss as high severity. Lock references: `frontend/package-lock.json:1255,1349,1484,1517,1700-1701`; complete advisories and affected ranges are in `npm-audit.json`. These are predominantly build/dev-tool dependencies; this is **not** a claim of seven exploitable vulnerabilities in the shipped React bundle. Do not run `npm audit fix --force` blindly.

**Finish requirement:** explicitly document local single-user operation or add authentication, origin restrictions, job quotas/cancellation, bounded worker concurrency and per-match versioning. Upgrade dependencies deliberately and retest. Acceptance: unauthorized mutations fail for network deployment, allowed origin policy is verified, simultaneous actions cannot corrupt state, and job floods are rejected/queued within a measured memory/CPU budget. Keep dev servers private meanwhile.

## Gap to the intended finished product

Completion goals are inferred from `README.md:3-11,266-300`, `plan.md:23-60,145-203`, and the newer knowledge-base plan—not a separate agreed release specification.

1. **Supported-corpus rules fidelity, not just parser classification.** The ability model still calls Oracle-text inference (`backend/rules_engine/ability_model.py:39-52`). Zero parser fallbacks does not prove correct semantics; the reproduced draw/cleanup seams demonstrate why. Freeze an explicit supported corpus, verify canonical data and complete effect clauses, surface unsupported cards before claiming trustworthy win rates.
2. **Knowledge-based AI is only partially implemented.** HEAD adds the knowledge model/repository; current tracked `backend/knowledge/` contains only `__init__.py` and `models.py`. The newer plan explicitly calls for corpus sync, verified seed data, AI consumers/profiles and sideboarding (`docs/plans/2026-09-09-ai-knowledge-base.md:5-21,63-110` and later phases). Current AI source has no knowledge/sideboard references; current main hydration still imports handwritten fallback data. The model's presence is not proof that AI uses it. Old counts of cached rulings/data drift in the plan were not reasserted as current database facts.
3. **Full human workflows must reach supported engine functionality.** Fix seat-aware actions, choices, mulligan/cleanup selection, zone browsing, honest effective stats, BO3 and restore/reconnect before cosmetic polish or deeper search.
4. **Release reproducibility and realistic validation.** Close clean-checkout assets, frontend tests/contracts, production proxy setup, durable job/restart behavior and an explicit local-versus-network security posture. Existing long-session/LAN limitations remain acknowledged in `README.md:291,300`.

The old finish plan contains historical or conflicting status notes; e.g. the obsolete incompatible-TestClient warning and past parser-fallback claims. Reconcile docs to reproducible current evidence instead of treating every unchecked paragraph as remaining implementation work.

## Completion roadmap and acceptance gates

### Gate 1 — Reliable local human-playtesting beta (highest priority)

- Unify hydration/serialization; fix acting-seat/action coverage and effective card views.
- Fix draw-step/cleanup event paths and user choices.
- Validate inputs and show useful errors; serialize actions and restore saved matches after refresh.
- Package fallback assets; establish clean checkout CI with backend suite, frontend build/lint/component tests and a browser flow.

**Acceptance:** from empty cache/database, import a supported deck, start human-vs-AI and human-vs-human, mulligan with deliberate choices, cast/target/respond, use activated/crew/exile actions, finish combat, choose cleanup discard, complete a BO3 with sideboarding, reload/restart and resume. Verify counters/effective stats and replacement/trigger events through HTTP/UI, not only helper tests. No internal 500s for bad user inputs; all configured gates green without developer-only files.

### Gate 2 — Trustworthy supported-corpus simulator

- Verify canonical corpus data/provenance; implement the knowledge plan through an actual AI consumer, not just storage.
- Share simulation and live-match hydration/transition rules; preserve seed provenance.
- Expand golden rules fixtures across unsupported/ambiguous families, and route unsupported semantics into explicit diagnostics rather than silent approximation.
- Run larger seeded, seat-balanced archetype matrices; retain per-decision legal traces, timeout reasons, illegal-action/cost/target counts and confidence intervals.

**Acceptance:** no unexplained rule/cost/target stalls in the agreed supported corpus; deterministic replay and restart snapshots match; each reported improvement has before/after decision-quality evidence. Predefine sample size and acceptable long-game timeout policy. Do not call a 2–0 smoke result evidence of balance or expert AI.

### Gate 3 — Packaged release and operational hardening

- Build/test the actual HTTPS/LAN deployment path, document install/backup/restore and supported worker topology.
- Add job limits/cancellation, retention policy, crash/restart behavior, network authorization if applicable, and deliberate dependency upgrades.
- Finish long-session ergonomics, error boundaries, accessibility and replay state reconstruction according to the chosen release scope.

**Acceptance:** clean-machine install, offline fallback, HTTPS API/media smoke, backend restart recovery, bounded concurrent jobs, long-session soak, saved-data restore, and security/dependency review. Arbitrary-card MTG completeness or seasoned-player AI requires additional explicit acceptance criteria beyond these gates.
